# Step 2-A — Document Storage and Upload: Implementation Plan

Status: **Approved and implemented (see PHASE-2A-REPORT.md)** · Date: 2026-11-18 · Part of [PHASE-2.0-PLAN.md](PHASE-2.0-PLAN.md)
(revision 2) · Baseline: `80a82e7`

Tags: **[V]** verified, **[R]** recommendation, **[D]** needs your decision.

## 1. Outcome

A broker with the new document permission can upload a PDF to a case, optionally for one
applicant. The original is stored privately under a generated key, byte-identical, with its
SHA-256. It can be listed and downloaded, and the download is verified against that hash.

Nothing is parsed, queued or processed in 2-A. No pages are read, no jobs are created and no
worker exists yet (2-B and 2-C). Page limits are enforced in 2-C, where the PDF is first
opened.

## 2. Facts this plan relies on [V]

- Routers are registered in `app.py`. Permissions are `requires(Permission.X)` dependencies
  in `api/deps.py`. Services take an `OperationContext`. `get_case(..., for_update=True)`
  is the case row lock that all case writes already use.
- Errors are problem+json with `urn:meip:problem:<slug>`. `IntegrityError` 23505 maps to 409.
- `Environment` is `local | test | staging | production`. Settings already fail at startup
  for unsafe combinations (dev auth outside local and test).
- Runtime dependencies are currently FastAPI, uvicorn, pydantic(-settings), SQLAlchemy,
  asyncpg, alembic, structlog, pyjwt and anyio.
- Docker and Podman are installed on this machine, but the Docker stack has never been run;
  that check belongs to 2-B. Node 22 is installed, so Azurite can also run without Docker.

## 3. Design

### 3.1 Permissions (P2-6)

| Permission | Roles | Used by |
|---|---|---|
| `document:read` | all roles, including read-only | list, metadata, download |
| `document:write` | firm admin, adviser, case administrator | upload |

**[R]** Reading gets a permission of its own too, even though every role holds it today.
Downloading an original payslip is more sensitive than reading case data, so a firm can
narrow it later without a code change. Both permissions go into the authorization matrix
and the audit-route tests.

### 3.2 Fail-closed gating (P2-8)

New settings:

| Setting | Default | Meaning |
|---|---|---|
| `documents_enabled` | `false` | Master switch for every document route (and, later, the worker) |
| `document_retention_approval` | unset | A reference to the approved D10 decision, e.g. `D10-2027-01` |
| `blob_backend` | `azure` | `azure` or `filesystem` |
| `document_max_bytes` | 20 MiB | Upload cap |

Validation at startup (the process refuses to start rather than run unsafely):
- In `staging` or `production`, `documents_enabled=true` requires
  `document_retention_approval`.
- The `filesystem` backend is allowed only in `local` and `test`.

When document routes are disabled they return **404** with
`urn:meip:problem:feature-disabled`. They are always registered, so the OpenAPI contract
stays stable.

Limitation, stated plainly: the platform **cannot tell** synthetic documents from real ones.
The approval reference is a deployment control, not content inspection.

### 3.3 Storage (`BlobStore` interface)

```python
class BlobStore(Protocol):
    async def put_new(self, key: BlobKey, source: BinaryIO, *, size: int, sha256: str) -> None
        # create-only: fails if the key exists; never overwrites
    async def open(self, key: BlobKey) -> AsyncIterator[bytes]
    async def exists(self, key: BlobKey) -> bool
```

There is **no delete method**: application code can't delete originals.

- **Keys** are generated by the server only: `{tenant_id}/{case_id}/{document_id}/{version_id}/original`.
  All parts are UUIDs, validated by regex in a `BlobKey` type. No file name or client text
  ever reaches a key, which rules out path traversal by construction.
- **`FilesystemBlobStore`** is for local and test use. It writes to a temporary file in the
  same directory, then links it into place, so writes are atomic and create-only.
- **`AzureBlobStore`** uses the official `azure-storage-blob` SDK, with uploads that fail if
  the blob already exists. **[R]** I'd use the SDK's **synchronous** client inside a worker
  thread (`anyio.to_thread`). Its async client needs `aiohttp` as an extra dependency, and the
  thread approach is enough at this scale. The container is private: there's no public access
  and no SAS URLs are given to browsers. The connection string comes from settings; managed
  identity comes in Phase 12.
- **Docker Compose** gains a pinned Azurite service. The container is created by a local
  bootstrap command (`meip-admin init-storage`), never by the API.

### 3.4 Upload API

`POST /api/v1/cases/{case_id}/documents`

**[R]** The request body is the **raw PDF** (`Content-Type: application/pdf`), not a
multipart form. Metadata travels in query parameters that contain no personal data:
`applicant_id` (optional) and `document_type=payslip`. An optional original file name goes
in an `Upload-Filename` header (percent-encoded), never in the URL.

Why not multipart: it would add `python-multipart`, and it spools the whole upload before our
code can enforce the size limit. A raw body lets the cap be enforced **while streaming**.

Steps in the service:
1. **Before reading the body:** check the feature flag and permission, that the case exists
   and is editable, and that the applicant is active and on this case. Reject any
   `Content-Length` over the cap with **413**.
2. **Stream** into a spooled temporary file (in memory up to 1 MiB, then disk), counting and
   hashing as it goes. Stop with **413** at cap + 1 byte, whatever the headers claimed. An
   empty body gets **422**.
3. **Validate:** the body must start with `%PDF-` (the PDF standard puts it at byte 0), and
   the declared `Content-Type` must be `application/pdf`. Otherwise **415**. Deeper checks
   (structure, encryption, page count) happen in 2-C, in the sandboxed worker.
4. **Take the case row lock**, then look for the same SHA-256 already in the case. If found,
   return **409** `duplicate-document` with `existing_document_id`. The lock serialises
   uploads to one case, so a duplicate race normally resolves here **before any blob is
   written**.
5. **Write the blob** under the generated key (create-only).
6. **In one transaction:** insert the `documents` and `document_versions` rows and the
   `document.uploaded` audit event, then commit. If the unique index fires anyway, it is
   mapped to 409 too (the database backstop for P2-5).
7. Respond **201** with document metadata. The response never includes the blob key.

The file name is sanitised (control characters removed, path separators stripped, at most
255 characters) and stored as **erasable** data. It is never logged, and never used in a
storage key or a response header.

### 3.5 Read API

| Route | Returns |
|---|---|
| `GET /cases/{id}/documents` | List of metadata, with the applicant, type, status, size and upload details |
| `GET /cases/{id}/documents/{document_id}` | One document's metadata, including its version |
| `GET /cases/{id}/documents/{document_id}/content` | The original bytes |

Download:
- The document's database row is looked up under RLS first. The blob path alone is never
  trusted.
- The blob is read into a spooled temporary file and its **SHA-256 is checked before any
  byte is sent**. If it doesn't match, the API returns **500** `integrity-error` and logs
  the document ID and reason only.
- Headers: `Content-Type: application/pdf`;
  `Content-Disposition: attachment; filename="document-<id>.pdf"` (never the stored name);
  `X-Content-Type-Options: nosniff`; `Cache-Control: no-store`; and a
  `Repr-Digest: sha-256=:…:` header for clients that want to check it themselves.

### 3.6 Data model (migration `0012_documents`)

`documents`:
- `id`, `tenant_id`, `case_id`, `applicant_id` (nullable), `document_type` (CHECK `'payslip'`).
- `status` (CHECK `'received'`; later steps extend it).
- `created_by_user_id`, `created_at`, `updated_at`, `version`.
- Composite FKs to the tenant, case and applicant, like the financial tables.

`document_versions`:
- `id`, `tenant_id`, `case_id`, `document_id`, `version_number` (CHECK `= 1` in 2.0).
- `sha256` (CHECK `^[0-9a-f]{64}$`), `size_bytes` (CHECK `> 0`), `media_type` (CHECK
  `'application/pdf'`), `blob_key` (UNIQUE, with a CHECK on its generated pattern).
- `original_filename` (nullable, erasable), `scan_status` (CHECK `'not_scanned'` for now),
  `uploaded_by_user_id`, `uploaded_at`.
- **`UNIQUE (tenant_id, case_id, sha256)`**: the P2-5 guarantee, which holds under
  concurrency because PostgreSQL's unique index makes the second insert wait and then fail.

| Aspect | Rule |
|---|---|
| RLS | Tenant policy on both tables, as on every other tenant table |
| Runtime grants | `documents`: SELECT and INSERT (UPDATE comes in 2-B/2-C, column-level). `document_versions`: **SELECT and INSERT only**. No DELETE on either. |
| Immutability | Trigger `document_versions_immutable` rejects UPDATE and DELETE **for every role**. Later steps add set-once columns explicitly. |
| Catalog | Both tables are TENANT_SCOPED in `schema_policy.py`; the new trigger goes in `EXPECTED_TRIGGERS` |
| Downgrade | Refuses while any document exists, so it never silently orphans stored originals |

### 3.7 Audit

| Event | Permanent record | Erasable details |
|---|---|---|
| `document.uploaded` | document and version IDs, applicant ID, type, size, media type | file name, SHA-256 |

**[R]** The SHA-256 counts as erasable. It could be used to confirm that a known document
was held.

Downloads are **not audited** in 2-A, which keeps the existing rule that only mutations are
audited. **[D]** Do you want access logging for originals? I'd recommend a separate
access-log design in 2-F or Phase 9 rather than mixing it into the mutation audit.

## 4. Orphaned blobs (known limitation)

If the process dies after step 5 and before step 6 commits, a blob exists with no database
row. The application identity can't delete, by design, so nothing cleans this up in 2-A.

Mitigation: an owner-run `meip-admin find-orphan-blobs` report command (read-only) lists
keys with no row. Deletion stays an operator action until the retention process (D10)
exists.

The case lock prevents duplicate-upload races from creating orphans in normal operation.

## 6. Tests

| Area | Tests |
|---|---|
| Round trip | Byte-identical download and matching SHA-256, for sizes below and above the 1 MiB spool threshold; `Repr-Digest` matches |
| Validation | 415 for a wrong content type; 415 for bad magic bytes (including a PDF header at byte 1); 413 from `Content-Length`; **413 from a lying or missing Content-Length while streaming**; 422 for an empty body |
| Duplicates (P2-5) | Sequential: 409 with `existing_document_id`. **Concurrent API uploads:** exactly one 201. **Raw SQL on two connections without the case lock:** the second insert waits on the index, then fails. The same file in a *different* case is allowed. |
| Case and applicant rules | Case not editable gives 409; applicant not on the case, or removed, gives 422 or 409 like the financial routes |
| Integrity | A tampered blob gives 500 `integrity-error`, and no bytes are sent |
| Storage | Keys are generated and validated, and a malformed key is rejected; `put_new` never overwrites; the store has no delete method (static test); the API never returns blob keys |
| Isolation | The new tables are in the catalog guard (RLS, grants, no DELETE, immutability trigger present); **cross-tenant probes** for every new route; the authorization matrix covers `document:read` and `document:write` |
| Fail-closed | Routes return 404 `feature-disabled` when off; startup fails in production when enabled without an approval reference; startup fails with the filesystem backend in staging or production |
| Audit and logs | Exactly one `document.uploaded` event per upload, with the file name and hash only in details; captured logs contain no file name |
| Migration | Round trip and model drift; the downgrade refuses while documents exist |
| Azure adapter | Opt-in test (`-m azurite`, skipped by default) against Azurite. **The report will say whether it actually ran.** Running it against a real Azure storage account is a separate, later verification. |

## 7. Security summary

- **Isolation:** no new path crosses tenants. Every read starts from an RLS-filtered row, and
  keys are server-generated UUIDs.
- **Untrusted input:** the API reads only the first five bytes and the length of an
  uploaded file. No PDF parser runs in the API process, now or later.
- **Resource exhaustion:** the streaming cap applies regardless of headers. Spooling beyond
  1 MiB goes to disk. Request rate limits and reverse-proxy body limits are deployment
  concerns for Phase 12, noted here.
- **Personal data:**
  - File names and hashes are erasable.
  - Nothing personal appears in URLs, blob keys or logs.
  - Originals are new personal data, so the inventory (categories 1 and 11) moves from
    "Planned" to "Exists (local and test only)".
